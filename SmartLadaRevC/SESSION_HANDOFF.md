# SmartLada Rev C - Session Handoff (2026-09-06, вечер)

Плата revC живая. USB `/dev/cu.usbmodem101` (порт **регулярно отваливается** - см. «Ловушки»).
Прошивка `SmartLadaRevC/`. Сборка `arduino-cli`, FQBN
`esp32:esp32:esp32c6:ZigbeeMode=ed,PartitionScheme=zigbee_8MB,CDCOnBoot=cdc,FlashSize=16M`.
Ядро **Arduino-ESP32 3.3.10** - версия критична, см. «Ловушки».

**Текущее: `1.0.19-revC`**, залита, проверена пользователем. Правило: компилировать до заливки.

Работа лежит на ветке **`revc-fw-1.0.10`** (имя отстало от версии), запушена в `origin`.
`main` про неё ещё не знает - влить после доковой правки.

## Состояние коммитов

- `0c9585b` fw 1.0.10 - Волна 1 (R1-R6) + вход в OTA + склейка цвета
- `77acd9b` fw 1.0.11 - soft start обратно на эффекты, EP14 только эффекты, restore-on-boot
- дальше 1.0.12-1.0.19 - в этом же коммите с handoff'ом

Не в git намеренно: `smarthome_backend/` (13 МБ, отдельная работа), `research/`.

## Что сделано и подтверждено пользователем на железе

- **Цветовой баг Алисы вылечен.** Не было прыжков в красный и «безымянного белого» на серии
  белый <-> пурпурный/синий/голубой/зелёный/красный.
- **BLE OTA работает end-to-end**, залито трижды без USB (42 с и 110 с на 1.1 МБ; скорость
  скачет, ошибок нет). Вход в режим обновления, экран, выход кнопкой - всё ок.
- **Restore при подаче питания** - состояние возвращается, включая режим.
- **Soft start снова действует на эффекты**: у «поворотника» вернулся ramp вместо 0-100-0.
  Пользователь держит 50-100 мс; быстрые эффекты не размазываются.
- **Диммирование ламп плавное.** Ступенчатость видна только на полоске OLED (см. «Не сделано»).
- **Поканальные яркости переживают смену цвета** (EP14 больше не раздаёт уровень по лампам).
- **Chase переписан** и принят: триггер-часы + собственная огибающая у каждой лампы.
- **Меню Timings**: прокрутка, липкое окно с запасом в строку, раскладка, переключатель по OK.

## Ключевые решения этой сессии (не переигрывать без причины)

1. **EP14 = только слой эффектов.** Цвет выбирает эффект, уровень EP14 = яркость эффекта
   ВСЕГДА. Выкл и белый значат одно: эффектов нет. EP14 **не** трогает `staticBri`.
   Групповая и поканальная яркость - целиком на EP10-13. Обсуждалось убрать белый совсем:
   решили оставить, иначе приложение показывает белый выбранным, а эффект продолжает крутиться.
2. **Плата не пушит цвет в EP14** и глушит собственные H/S-отчёты стека (APS-хук).
   Цена: эффект, выбранный в МЕНЮ платы, не подсвечивается цветом в приложении. Это
   осознанно; возврат подсветки возвращает и класс багов.
3. **Одна tau на всё** (`config::s.softMs`, Lamp Setup). Не вводить снова режимозависимое
   сглаживание канала - именно оно убило ramp у Turn. Яркость эффекта сглаживается отдельно
   мастер-easing'ом с собственной константой `MASTER_SMOOTH_MS = 500` в `.ino`.
4. **Число параметров эффекта выводится из массива** (`NPARAMS()`), руками не писать.

## Что НЕ сделано / не проверено

**BLE OTA: заливать ТОЛЬКО с платой на PD 12 В.**
- На USB 5 В скорость падала до ~6.5 КБ/с и передача срывалась на 26% и 35%: клиент сообщал
  `stalled (no ack)` - линк жив, плата перестаёт подтверждать блоки, ошибки записи нет.
- На PD 12 В тот же образ, тот же клиент: 1.1 МБ за 56 с на 19-23 КБ/с, без сбоев.
  Прогонов достаточно, чтобы связать это с питанием, а не с радиообстановкой (первая гипотеза
  была неверной). Механизм не выясняли: вероятно просадка рельса при пиках передатчика.
- Заливка по USB (`arduino-cli upload`) не затронута - речь только про BLE.

**Проверено на железе:**
- R6, обрыв линка сразу ПОСЛЕ `FINISH`: `tools/ble_ota.py --drop-after-finish` рвёт соединение,
  плата всё равно коммитит образ и уходит в рабочую прошивку. Проверка объективная: после
  ребута `SmartLada` пропадает из эфира (в рабочем режиме BLE не поднимается).

**Не проверено на железе:**
- R5: подавление эха при команде от Алисы ровно в окно report-back. Потерь не наблюдали.

**Известные слабости обхода EP14 (`zigbee.cpp`):**
- **Тихий отказ установки.** Если `esp_zb_lock_acquire(1000)` не успел - в Serial уходит одна
  строка, прошивка работает БЕЗ обхода. Нужен ретрай в `update()` или признак на экране Info.
- **Окно повторного вооружения.** `stop_attr_reporting` срабатывает только на входящей
  Color Control команде. После `Configure Reporting` от координатора (репаринг, реинициализация)
  автоотчёт снова взведён и может выстрелить до следующей команды.
- **Корневая причина не установлена.** Обход опирается на поведение конкретной версии
  приложения/бэкенда Яндекса и может отвалиться после их обновления. Подробности, опровергнутые
  гипотезы и логи: `codex_reviews/EP14_SESSION_RESULT_for_LLM.md`.

**Косметика:**
- Полоска яркости на OLED рисует КОМАНДУ (`config::s.master`), а не сглаженное значение,
  поэтому дёргается пачками. Лампы при этом плавные. Чинится подачей сглаженного значения
  в меню - пара строк, решили не трогать.

**Документация (главный долг):**
- `README.md` и `DEV_PLAN.md` не прошли правку после этой сессии: там остались заявления
  сильнее фактов и устаревшая модель EP14 (Static x master, белый как групповой диммер).
  `DEV_PLAN.md` также описывает report-back EP14 с цветом - этого больше нет.
- Нигде не зафиксировано, что APS-хук завязан на внутренний символ ядра и версию 3.3.10.

**Отложено сознательно:** WiFi / веб-интерфейс, новые эффекты.

## План дальнейших правок (по приоритету)

1. **Доковый проход** + влить ветку в `main`. Дешево, защищает накопленное.
2. **Упрочнение обхода EP14**: ретрай установки + индикация; перекрыть окно повторного
   вооружения (например, глушить репортинг и по факту `Configure Reporting`, а не только
   по Color Control команде).
3. **Проверить R6 обрыв после FINISH** - искусственно рвать линк сразу за `FINISH`.
4. **Кросс-проверка на другом координаторе** (zigbee2mqtt / ZHA): если колесо там не прыгает,
   дело в интерпретации Алисы, и правильное лечение - согласованность атрибутов
   (`ColorMode` 0x0008 vs `EnhancedColorMode` 0x4001 vs `CurrentX/Y`), а не глушение отчётов.
5. Мелочь: сглаженное значение в полоску OLED.

## Ловушки, на которые уже наступали

- **`RTC_DATA_ATTR` НЕ переживает `ESP.restart()`.** Секция `.rtc.data` - загрузочный сегмент,
  бутлоадер восстанавливает её из образа при каждом ребуте; переживает только выход из
  deep sleep. Для флага режима OTA и счётчика загрузок нужен `RTC_NOINIT_ATTR` + магик-слово
  (мусор после подачи питания). Из-за этого BLE OTA был недостижим и `[boot #N]` всегда был 1.
- **Одна команда «move to hue and saturation» приходит ДВУМЯ записями атрибутов.** Библиотека
  вызывает HSV-колбэк на каждой, добирая вторую половину из таблицы атрибутов - первый вызов
  несёт полурассогласованную пару. Отсюда склейка 150 мс в `zigbee.cpp`. Сравнение дедлайна
  ОБЯЗАНО быть знаковым: метка ставится на Zigbee-задаче и бывает новее, чем `now` из `loop()`.
- **Ручные счётчики расходятся с массивами.** `EFFECTS[]` держал `2` при пяти параметрах:
  три параметра были невидимы в меню, а старое значение из NVS грузилось не в тот слот.
- **Экраны меню молча предполагали, что элементов мало.** В Timings помещается 4 строки по 12 px.
- **Уровень от Алисы идёт пачками по 10 команд с шагом 101 мс, потом пауза ~1 с.** Это темп
  доставки, а не наша обработка: сгладить паузу можно только отставанием на её длину.
- **Белый у Алисы - это `hue=162 sat=25`**, а не sat=0. Порог `SAT_THRESH=40` держит, но зазор
  всего 15 единиц: другой клиент с белым sat~40 будет распознан как цвет.
- **Порт USB платы часто исчезает** посреди работы. Если `/dev/cu.usbmodem101` пропал - это не
  падение прошивки; заливать можно по BLE, вход через меню Settings -> System -> Update Over BLE.
- **ОТКРЫТИЕ USB-порта ПЕРЕЗАГРУЖАЕТ плату** (`reset=USB` в загрузочной строке), даже когда
  DTR/RTS сняты до открытия. Следствия: запуск любого мониторинга = ребут; смотреть Serial во
  время BLE-сессии нельзя - открытие порта выбьет плату из режима обновления. Диагностику
  OTA приходится вести по статусам самого BLE-клиента.
  Коды сброса декодируются полностью с 1.0.21 (`USB`/`JTAG`/`EFUSE`/`PWRGLITCH`/`LOCKUP`
  раньше сваливались в `UNKNOWN` - настоящий сбой было не отличить от ребута со стороны хоста).
- **clangd в этом репо ругается всегда** (нет путей Arduino). Проверка одна: `arduino-cli compile`.

## Команды

```
# сборка
arduino-cli compile --fqbn esp32:esp32:esp32c6:ZigbeeMode=ed,PartitionScheme=zigbee_8MB,CDCOnBoot=cdc,FlashSize=16M \
  --build-path /tmp/smartlada-verify SmartLadaRevC

# заливка по USB
arduino-cli upload -p /dev/cu.usbmodem101 --fqbn <тот же FQBN> \
  --input-dir /tmp/smartlada-verify SmartLadaRevC

# заливка по BLE (плата должна быть в режиме обновления)
uv run --with bleak python3 tools/ble_ota.py /tmp/smartlada-verify/SmartLadaRevC.ino.bin

# лог с платы (pyserial; НЕ дёргать DTR/RTS, иначе ребут)
uv run --with pyserial python3 - <<'PY'
import serial, time
s = serial.Serial(); s.port='/dev/cu.usbmodem101'; s.baudrate=115200
s.dtr=False; s.rts=False; s.timeout=0.2; s.open()
t=time.time()
while time.time()-t < 60: print(s.read(4096).decode('utf-8','replace'), end='')
PY
```
