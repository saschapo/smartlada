# SmartLada / Алиса / Zigbee — архитектура 4-канальной фары

Дата: 2026-08-20

## Цель

Физическое устройство: одна фара с 4 независимо диммируемыми лампами, управляемая ESP32-C6 по Zigbee.

Желаемый голосовой UX:

- «Алиса, включи поворотник»
- «Алиса, поставь яркость поворотника 30 процентов»
- «Алиса, включи стоп-сигнал»
- «Алиса, поставь яркость стоп-сигнала 70 процентов»

В перспективе желательно проверить и более естественные формы:

- «Алиса, включи поворотник на 30 процентов»
- «Алиса, включи стоп-сигнал у фары на 70 процентов»

## Что подтверждено документацией Яндекса

### 1. Прямое управление Zigbee

Хабы Яндекса поддерживают Zigbee 3.0 и стандартные Zigbee ZCL-кластеры.

Из полезного для проекта официально поддерживаются:

| ZCL cluster | Назначение |
|---|---|
| `OnOffCluster` | включение / выключение / toggle |
| `LevelCluster` | изменение уровня, в нашем случае яркости |
| `ColorControlCluster` | цветовая температура |
| `IlluminanceMeasurementCluster` | освещённость |
| `TemperatureMeasurementCluster` | температура |
| `PressureMeasurementCluster` | давление |
| `RelativeHumidityCluster` | влажность |
| `OccupancySensingCluster` | присутствие |

Для управления лампами главное:

```text
OnOffCluster
LevelCluster
```

Яндекс пишет, что если устройство корректно передаёт `Device ID` и атрибуты, оно может подключиться напрямую к платформе без отдельного облачного навыка.

### 2. `DimmableLight`

Для Zigbee ZHA Яндекс явно поддерживает:

```text
DimmableLight = 0x0101
```

Тип в платформе:

```text
devices.types.light
```

Разрешённые кластеры:

```text
OnOffCluster
LevelCluster
ColorControlCluster
```

Следовательно, канал PWM логично представить как Zigbee `DimmableLight`.

### 3. Яркость в модели Алисы

В Smart Home API Яндекса яркость представляется как:

```text
devices.capabilities.range
instance = brightness
unit = unit.percent
```

Диапазон может быть 0–100 или 1–100 в зависимости от описания устройства.

Документация приводит стандартные голосовые конструкции вроде:

> «Алиса, убавь яркость света в спальне.»

То есть концепция «яркость конкретного именованного устройства» является штатной для Алисы.

## Предлагаемая архитектура SmartLada

Не представлять всю фару одним логическим `light` с четырьмя нестандартными параметрами.

Вместо этого:

```text
ESP32-C6
│
├── Endpoint 10 — DimmableLight
│   ├── OnOff
│   └── LevelControl
│
├── Endpoint 11 — DimmableLight
│   ├── OnOff
│   └── LevelControl
│
├── Endpoint 12 — DimmableLight
│   ├── OnOff
│   └── LevelControl
│
└── Endpoint 13 — DimmableLight
    ├── OnOff
    └── LevelControl
```

Предполагаемое соответствие:

```text
EP10 → поворотник
EP11 → стоп-сигнал
EP12 → габарит
EP13 → задний ход
```

На уровне MCU:

```text
EP10 Level → PWM CH1
EP11 Level → PWM CH2
EP12 Level → PWM CH3
EP13 Level → PWM CH4
```

Таким образом, физически это один ESP32-C6 / один Zigbee node / один IEEE address, но внутри него четыре Zigbee endpoint.

## Имена и голосовые команды

### Важный вывод

В стандартном Zigbee endpoint descriptor нет штатного поля типа:

```text
voice_name = "Поворотник"
alias = "Стоп-сигнал"
tag = "Габарит"
```

которое Алиса обязана использовать как имя для NLP.

Zigbee может передавать идентификационные metadata через Basic cluster, например:

```text
ManufacturerName
ModelIdentifier
ProductCode
```

Но это metadata модели/устройства, а не надёжный механизм задания голосового имени отдельного endpoint.

Поэтому нельзя строить архитектуру на предположении:

```text
EP10 → автоматически появится в Алисе как «Поворотник»
```

### Практический вариант

После pairing Алиса должна увидеть независимые логические сущности, если Яндекс корректно раскрывает multi-endpoint устройство.

После этого пользователь вручную задаёт имена в приложении **Дом с Алисой**:

```text
EP10 → «Поворотник»
EP11 → «Стоп-сигнал»
EP12 → «Габарит»
EP13 → «Задний ход»
```

Яндекс официально позволяет менять:

- имя;
- дом;
- комнату;
- группу

для устройства в приложении.

Именно пользовательское имя логического устройства разумно использовать как основной semantic identifier для голосовых команд.

## Предполагаемый голосовой UX

Если четыре endpoint действительно появляются как четыре отдельных устройства:

```text
«Алиса, включи поворотник»
→ EP10 OnOff = ON
```

```text
«Алиса, поставь яркость поворотника 30 процентов»
→ EP10 Level ≈ 30 %
```

```text
«Алиса, включи стоп-сигнал»
→ EP11 OnOff = ON
```

```text
«Алиса, поставь яркость стоп-сигнала 70 процентов»
→ EP11 Level ≈ 70 %
```

ESP32-C6 затем переводит Zigbee Level в соответствующий duty cycle PWM.

Например:

```text
Level 0 %   → PWM 0 %
Level 30 %  → PWM 30 %
Level 70 %  → PWM 70 %
Level 100 % → PWM 100 %
```

Фактическое отображение Zigbee `CurrentLevel` (обычно шкала ZCL) на внутреннюю шкалу PWM можно сделать отдельно.

## Почему не делать одну «Фару» с четырьмя brightness

У `devices.capabilities.range` есть стандартный `instance`, например:

```text
brightness
temperature
volume
...
```

Нет штатной схемы:

```text
brightness.turn
brightness.stop
brightness.parking
brightness.reverse
```

Поэтому четыре физических световых канала лучше моделировать как четыре логических light-устройства, а не как четыре одинаковых capability внутри одной сущности.

## Идея верхнего уровня: «Фара»

Можно рассматривать `Фара` не как самостоятельный PWM endpoint, а как логическую группу/контекст, содержащий:

```text
Фара
├── Поворотник
├── Стоп-сигнал
├── Габарит
└── Задний ход
```

Тогда интересно экспериментально проверить NLP Алисы:

```text
«включи поворотник у фары»
«поставь стоп-сигнал у фары на 70 процентов»
```

Однако выражение `у фары` — это уже логика NLP/группировки Алисы, а не Zigbee ZCL. Нельзя гарантировать её работу только правильным descriptor'ом Zigbee.

## Главный неподтверждённый вопрос

Стандарт Zigbee позволяет одному node содержать несколько application endpoints.

Но в найденной публичной документации Яндекса не найдено явной гарантии:

```text
1 Zigbee node
+ 4 × DimmableLight endpoint
=
4 отдельно именуемых устройства в «Доме с Алисой»
```

Это ключевой эксперимент до окончательной реализации.

Возможны варианты:

### Вариант A — идеальный

```text
ESP32-C6
 ├─ EP10 → карточка устройства 1
 ├─ EP11 → карточка устройства 2
 ├─ EP12 → карточка устройства 3
 └─ EP13 → карточка устройства 4
```

Тогда после ручного переименования вся архитектура работает практически идеально.

### Вариант B — Яндекс агрегирует endpoints

Если Алиса отображает весь node одной карточкой или игнорирует дополнительные endpoints, прямой Zigbee-подход не позволит получить требуемый UX без дополнительного слоя.

Тогда альтернативы:

1. Zigbee → Home Assistant / другой bridge → Яндекс;
2. собственная интеграция Yandex Smart Home API;
3. другой протокол/bridge, позволяющий публиковать четыре логические entities.

## Минимальный экспериментальный firmware

До переноса полной SmartLada на Zigbee имеет смысл сделать отдельный test firmware.

```text
ESP32-C6

EP10:
    Device ID: 0x0101 DimmableLight
    Basic
    Identify
    OnOff
    LevelControl

EP11:
    Device ID: 0x0101 DimmableLight
    Basic
    Identify
    OnOff
    LevelControl

EP12:
    Device ID: 0x0101 DimmableLight
    Basic
    Identify
    OnOff
    LevelControl

EP13:
    Device ID: 0x0101 DimmableLight
    Basic
    Identify
    OnOff
    LevelControl
```

На первом тесте PWM можно вообще не подключать.

Все входящие команды логировать:

```text
EP10 ON
EP10 LEVEL = 76

EP11 LEVEL = 178
...
```

После pairing проверить:

1. Сколько устройств появилось в «Доме с Алисой».
2. Можно ли каждому дать собственное имя.
3. Работают ли независимые `On/Off`.
4. Работает ли независимая яркость.
5. Какие русские голосовые формулировки распознаются.
6. Можно ли объединить четыре сущности в группу `Фара`.
7. Работает ли контекстная фраза вида «поворотник у фары».
8. Что происходит после reboot / rejoin — сохраняется ли mapping endpoint → entity.

## Статус утверждений

### Подтверждено

- Яндекс поддерживает Zigbee 3.0.
- Поддерживаются `OnOffCluster` и `LevelCluster`.
- `DimmableLight = 0x0101` официально распознаётся как `devices.types.light`.
- `DimmableLight` может иметь `OnOffCluster` + `LevelCluster`.
- В Smart Home API есть штатная capability `brightness`.
- Пользователь может менять имя устройства в «Доме с Алисой».

### Архитектурный вывод

Оптимальное представление 4-канальной фары:

```text
4 физических лампы
→ 4 Zigbee DimmableLight endpoints
→ 4 логических light-устройства
→ индивидуальные имена
→ индивидуальные голосовые команды
```

### Требует проверки

- раскроет ли Яндекс четыре endpoints одного ESP32-C6 как четыре отдельных entities;
- можно ли каждой entity независимо назначить имя;
- насколько естественно Алиса понимает:
  - «включи поворотник на 30 процентов»;
  - «поставь поворотник на 30 процентов»;
  - «яркость поворотника 30 процентов»;
  - «включи стоп-сигнал у фары на 70 процентов»;
- можно ли использовать группу `Фара` как устойчивый NLP-контекст.
