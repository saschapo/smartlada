# SmartLada × Алиса: Wi-Fi (облако/Matter) против Zigbee — сравнение путей

Дата: 2026-08-20. Исследование по запросу: «может, сделать через Wi-Fi, а не Zigbee» +
«имитировать чужое устройство с 4 диммерами в одном». Ниже — что подтвердила документация
Яндекса/Espressif и вывод.

## ГЛАВНОЕ ограничение (общее для ВСЕХ путей)

Модель устройства в Смарт-Хоме Яндекса: способность `range` имеет **фиксированный** список
instance: `brightness, channel, humidity, open, temperature, volume`. **`brightness`
ровно один на устройство** — нет `brightness_1/2/3/4`.

Следствие: **«4 диммера в одной карточке» невозможны нигде** — ни в Zigbee, ни в облачном
Wi-Fi API, ни в Matter. Это ограничение платформы Яндекса, а не Zigbee. Реально достижимо
везде одно и то же: **4 отдельных именованных light-устройства от одного физического блока**.
Требование «4-в-1-карточке» надо окончательно снять.

Значит выбор пути — не про «одну карточку», а про: (1) контроль над **именами/комнатами**
(наша реальная боль — 4× «Лампочка» вручную), (2) объём инфраструктуры, (3) радио.

## Путь A — Zigbee multi-endpoint (текущий, ПОДТВЕРЖДЁН)

4× DimmableLight EP10..13 на одном C6. Вариант A получен: 4 независимые лампы, диммер,
группа «Фара». См. [`zigbee_alice_test_results.md`](zigbee_alice_test_results.md).

- **+** Работает уже сейчас; ноль облака; низкое энергопотребление; нужен только хаб-коорд.
  (Станция Midi есть).
- **-** **Именами прошивка не управляет** (только Manufacturer/Model, Яндекс их для имени
  карточки, похоже, игнорит) → ручное переименование 4 ламп + ручная группа. Разово, но муторно.
- **-** C6 делит одно 2.4 ГГц радио: Zigbee ⇒ нет одновременного Wi-Fi/веба.

## Путь B — Облачный Wi-Fi (Yandex Smart Home provider API)

«Wi-Fi» у Яндекса для сторонних = **облачная интеграция**, не локальный протокол. Локального
открытого LAN-API для чужих устройств нет.

Архитектура (3 уровня): **ESP32 → твой публичный веб-сервис → Yandex Smart Home API**.
Твой backend реализует протокол провайдера: OAuth2 + REST (`/v1.0/user/devices`,
`/user/devices/query`, `/user/devices/action`, health). Устройства ты **описываешь сам**.

- **+** ПОЛНЫЙ контроль: возвращаешь 4 устройства сразу с русскими именами
  («Поворотник»…) и комнатами — **боль с именами решается программно**, без ручной возни.
- **+** Чистый Wi-Fi, радио-конфликта нет.
- **-** Тяжело: нужен **публичный сервер + домен + HTTPS + OAuth**, публикация навыка в
  Яндекс.Диалогах, account linking, SLA ответа ≤3 c, хостинг и вечная поддержка. ESP32 сам
  endpoint'ом быть не может — нужен облачный брокер (MQTT/HTTP) между ним и твоим backend.
- Оправдано, только если делаешь «продукт» с аккуратным UX и готов держать сервер.

## Путь C — Matter over Wi-Fi на ESP32-C6 (РЕКОМЕНДУЮ протестировать)

Яндекс **официально поддерживает Matter-over-Wi-Fi**, включая лампы с яркостью/цветом; нужен
хаб/Станция как Matter-контроллер (Midi подходит). Thread — НЕ поддерживается, только Wi-Fi.
ESP32-C6 умеет Matter over Wi-Fi (commissioning по BLE). В установленном Arduino-ядре
**есть библиотека Matter** с примерами `MatterDimmableLight`, `MatterComposedLights`,
`MatterLambdaSingleCallbackManyEPs` — т.е. **несколько lamp-endpoint в одном узле** собираются
так же просто, как наш Zigbee-тест.

- **+** Чистый Wi-Fi (то, что ты хотел), **без своего облака/сервера**, стандарт.
- **+** Matter bridge/composed-модель несёт **имя на каждое под-устройство** (NodeLabel/
  ProductName) → есть шанс получить 4 **осмысленно названные** лампы БЕЗ backend'а. Это
  потенциально решает боль с именами дешевле, чем облако.
- **+** Радио-конфликта Zigbee↔Wi-Fi нет (всё Wi-Fi).
- **-/?** Ключевые НЕИЗВЕСТНЫЕ (проверять эмпирически, как делали с Zigbee):
  1. раскроет ли Яндекс multi-endpoint / composed Matter-узел как **4 отдельных** устройства;
  2. подхватит ли **имена** из Matter (главный вопрос — ради него весь путь);
  3. нюансы commissioning C6 (BLE) со Станцией.
- **-** Wi-Fi-устройство всегда online (питание) — для сетевой фары это ок.

## Идея «имитировать чужое устройство с 4 диммерами»

На рынке есть 4-канальные Tuya Zigbee диммеры «works with Alice». Но:

- У Яндекса они всё равно раскрываются как **N отдельных устройств** (= ровно то, что у нас
  уже есть в варианте A), а не как «4 диммера в одной карточке» — платформенное ограничение
  `brightness` не обходится подделкой identity.
- Клонирование Manufacturer/Model чужого модуля может лишь заставить Яндекс применить более
  удачный **handler**, но **русские имена** оно не впишет, авто-группу не создаст.
- Плюс это подделка чужих идентификаторов (серо для распространения; для личного reverse
  engineering — ок).
- **Вывод: низкий выхлоп.** Deprioritize против Matter.

## Итоговое сравнение

| Критерий | A. Zigbee (есть) | B. Облако Wi-Fi | C. Matter Wi-Fi |
|---|---|---|---|
| 4 именованные лампы | да (имена вручную) | да (имена программно) | да (имена — вопрос) |
| «4 диммера в 1 карте» | нет | нет | нет |
| Контроль имён/комнат прошивкой | нет | полный | частичный (Matter names) |
| Своё облако/сервер | нет | **нужен** | нет |
| Транспорт | Zigbee | Wi-Fi (cloud) | Wi-Fi (local commissioning) |
| Радио-конфликт с вебом | да | нет | нет |
| Готовность сейчас | **работает** | месяцы работы | тест ~как Zigbee |
| Сложность | низкая | высокая | средняя |

## Рекомендация

1. **Следующий эксперимент — Matter-over-Wi-Fi тест** (аналог нашего Zigbee-теста): один
   ESP32-C6, 4× Matter DimmableLight с именами, спарить со Станцией, проверить —
   (a) 4 ли устройства, (b) подхватились ли имена, (c) диммер. Это прямой ответ на «может,
   через Wi-Fi», и при удаче **дешевле решает боль с именами**, чем облако.
2. **Zigbee multi-endpoint (A) оставить как проверенный baseline** — если Matter у Яндекса
   окажется капризным, продукт можно вести на нём.
3. **Облако (B)** — тяжёлый резерв, только если захочется «продуктовый» UX с программными
   именами/комнатами и готовность держать сервер.
4. **Имитацию чужого устройства — отложить** (низкий выхлоп).
